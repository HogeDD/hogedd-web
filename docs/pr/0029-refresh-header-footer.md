# HeaderとFooterの共通UIを見直す

## 背景

ホーム画面のHero、Apps、Aboutを調整した結果、既存のHeaderとFooterが現在のデザインや情報構成に合わなくなっていた。

特にモバイルではHeaderが最初に強く目に入り、複数行になることでコンテンツより目立っていた。Footerにはページごとに異なる説明文や操作が渡されており、共通UIでありながら表示内容が安定していなかった。

また、UIを一度に作り込みすぎると完成イメージの認識がずれ、手戻りが大きくなることが分かった。HogeDDを参加者全員のプロダクトとして扱うため、実装の進め方も合わせて見直す。

## 決定したこと

- HeaderとFooterを、ページから表示内容を渡さない共通コンポーネントにする。
- Headerのナビゲーション定義を`app/_lib/site-navigation.ts`へまとめる。
- Headerには提供されたHogeDDロゴ、HogeDD、Apps、About、YouTubeを表示する。
- モバイルのHeaderは初期状態で隠し、下へスクロールした後に上へスクロールすると表示する。
- タブレット以上ではHeaderを常に表示する。
- Aboutの導線は専用ページを作るまで`/#about`とする。
- Footerはページ背景と同じ色を使い、HogeDD、Hoge Driven Development、Apps、About、YouTube、X共有だけを配置する。
- FooterのApps配下に個別アプリを並べる第2階層は、`/apps`ページの情報設計を整えた後に再検討する。
- UI、機能、設計の変更は確認可能な単位で反映し、明示的な合意なしに複数の判断を一度に確定しない。

## 理由

Headerの役割をブランドと主要導線に絞ることで、どのページでも同じ見た目と操作を提供できる。ナビゲーション定義を一か所へまとめることで、項目追加時にHeader内のJSXを組み替える必要もない。

モバイルでは画面の高さが限られるため、最初の表示ではコンテンツを優先する。一方、ページを戻る方向へスクロールしたときは移動意図があると考え、Headerを表示する。PCやタブレットでは表示領域に余裕があるため、導線を常時表示する。

Footerはサイトマップとして将来拡張できるが、現時点で第2階層まで表示すると情報設計より先に見た目だけが確定する。まず必要な第1階層に絞り、`/apps`ページを整備した段階で実際の分類に基づいて追加する。

UIは文章だけでは完成イメージを共有しにくい。小さく反映して確認する方が、開発速度だけを優先して作り直すより最終的な手戻りを減らせる。

## 検討した代替案

### モバイルでもHeaderを常に表示する

導線は見つけやすいが、最初の画面でHeaderの存在感が強くなる。コンテンツを優先するため採用しない。

### Footerを濃色背景にする

画面の終端は明確になるが、Footerだけが強く主張し、現在のページ背景から分断されて見えた。ページ背景と統一する。

### Footerに個別アプリを並べる

サイトマップとしては有効だが、`/apps`ページの分類やsectionが未確定である。仮の階層を固定しないため今回は見送る。

### ページごとにHeaderとFooterの内容を渡す

各ページに最適化できる一方、共通導線と文言がページごとにずれる。サイト全体のUIとして安定させるため採用しない。

## トレードオフ

- モバイルの最初の画面ではHeaderの導線が見えない。
- Footerの情報量を絞ったため、個別アプリへの直接導線はまだない。
- 共通コンポーネントの内容を変えると、利用している全ページへ影響する。
- UI変更ごとの確認が増えるため、一回の作業量は小さくなる。

## テスト・検証内容

- Prettierで対象ファイルのformatを確認。
- ESLintでHeaderとFooterを含む実装を確認。
- TypeScriptの型チェックを確認。
- Vitestのunit testを確認。
- Next.jsのproduction buildを確認。

## 今後の見直し条件

- `/about`専用ページを作るとき。
- `/apps`ページのsectionや分類を決めたとき。
- Headerへ新しい主要導線を追加するとき。
- モバイルのHeader表示条件について利用者から問題が報告されたとき。
- X共有の文言や共有先URLを設定可能にするとき。
