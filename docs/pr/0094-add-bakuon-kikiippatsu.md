# #94 爆音危機一髪を追加

## 背景

Issue #94 では、複数人で同じ端末を囲み、1つだけ爆音が鳴るボタンを避けながら順番に押すアプリを作ることが求められた。ターン管理や他機能への変更は含めず、スマホで遊ぶことを重視する。

## 決定したこと

- route slug は `bakuon-kikiippatsu` とした。
- ブラウザ内だけで完結するため、`_domain` / `_usecases` / `_infrastructure` は作らず、`_components` と `_lib` で構成した。
- 人数は2人から8人、ボタン数は人数×3個にした。
- 爆音ボタンは1つだけランダムに決め、押した時点で終了する。
- 誰の番かはアプリで管理しない。
- 音は外部素材を使わず、ユーザー操作後に Web Audio で短く鳴らす。
- `appLinks` には `preparing` として登録し、公開準備やYouTube導線は混ぜない。

## 理由

MVPとして必要なのは、同じ画面を囲んで順番に押せることと、1つだけ外れがある緊張感である。DB、外部API、認証、オンライン同期は不要なため、単純なアプリ構成で十分だった。

音量については、Issueの面白さとして「音量最大にすることを要求する」UIは入れた。一方で、アプリ側で過度な音量や長時間の音を生成すると体験が荒くなるため、短い演出音に留めた。

## 検討した代替案

- 黒ひげ危機一発に寄せて剣や樽の見た目にする案: MVPでは見た目の作り込みが主目的ではないため見送った。
- プレイヤー名と手番を管理する案: Issueの「誰の番とかの指定」はやらないことに含まれるため採用しなかった。
- 音声ファイルを追加する案: 素材管理と音量調整の判断が増えるため、MVPでは Web Audio にした。

## トレードオフ

- Web Audio はユーザー操作後でないと鳴らないブラウザがある。今回はボタン押下が必ずユーザー操作なので成立する。
- 端末の実音量はブラウザから検出できないため、音量MAXはユーザーへの確認に留まる。
- appLinks登録により一覧側のデータファイルを触るが、新規アプリの構成検査と導線のために必要な変更とした。

## テスト・検証内容

- `_lib/game.ts` の人数制約、ボタン数、爆音ボタン数、押下後の状態遷移をunit testで固定する。
- `app-page-structure.test.ts` により App / About / Guide / layout / metadata の共通構成を検査する。

## 今後の見直し条件

- 実機で音が弱い、強すぎる、または鳴らない端末がある場合は、音量・波形・フォールバック表示を別Issueで調整する。
- 見た目や演出を黒ひげ危機一発風へ寄せる場合は、MVPとは別Issueで扱う。
