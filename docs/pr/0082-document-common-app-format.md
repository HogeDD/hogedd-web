# アプリ開発サイクルへ共通フォーマットを反映する

## 背景

#72でApp / About / Guideの情報設計を決め、#77〜#80でゲームと非ゲームの既存アプリへ適用した。#81では新規アプリを自動検出し、route、共通shell、metadata path、Guideの必須propsをCIで検査できるようにした。

実装と自動検査は揃ったが、新しいアプリを作る人とAIが、着手時に必要な入力、短いAbout・Guideの扱い、PR前の確認項目を一続きで判断できるdocsが不足していた。

## 決定したこと

- `AGENTS.md`から新規アプリ追加チェックリストを参照する。
- App / About / Guideが短い場合も、ページやGuideの5セクションを省略しない。
- 内容が少ない場合は各役割を最低1項目で表現し、仮URLやAIが代筆した制作動機で埋めない。
- 開発サイクルへ、構成、共通ページ、テスト、表示、公開範囲のチェックリストを追加する。
- 将来Skill化するときに必要な入力、支援する判断、見直し条件を記録する。

## 理由

共通フォーマットはfileを生成するだけでは守れない。MVPと公開準備の分離、本人文章の待ち地点、themeの人間確認、単純構成とClean Architectureの判断には、実装前の入力確認が必要になる。

チェックリストを現在のAST検査と対応させることで、docsだけで判断する部分とCIが自動検査する部分を区別できる。短いGuideでも構造を省略しない方針を明記すると、アプリごとの情報量の差を許容しながら、ナビとページ構成を統一できる。

## 検討した代替案

### App / About / Guideのテンプレートコードを大量に掲載する

コピー時点では速いが、共通shellのprops変更でdocsが古くなりやすい。最小例と参照実装、チェックリストを正とする。

### 短いアプリではAboutまたはGuideを省略する

実装量は減るが、#72と#81で固定した共通契約が崩れ、ユーザーがアプリごとにナビ構造を学び直すため採用しない。

### このIssueでCodex Skillを作る

まだ新規アプリでチェックリストを繰り返し検証していない。必要な入力と判断だけを記録し、自動化は実績が揃ってから別Issueで扱う。

## トレードオフ

- 単純なアプリでも3ページとGuideの5セクションを書く必要がある。
- チェックリストには人が確認する項目とCIが検査する項目が混在する。
- 共通構成を変更した場合、AST検査、AGENTS.md、開発サイクルガイドを同時に更新する必要がある。

## テスト・検証内容

- #72、#77、#78、#79、#80、#81のdecision logと現在の実装を照合した。
- `app-page-structure.test.ts`が自動検査する契約とチェックリストを一致させた。
- docs以外のコードとテストは変更していない。
- `npm run format:check`を実行する。

## 今後の見直し条件

- 新しいアプリでチェックリストを使い、不足する入力や不要な項目が見つかったとき。
- App / About / Guide、theme、metadata、公開フローの共通契約を変更するとき。
- 同じ入力確認とfile追加が複数回繰り返され、Skill化の費用対効果を判断できるようになったとき。
