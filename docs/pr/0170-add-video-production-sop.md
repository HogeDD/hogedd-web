# 動画制作SOP(3日サイクル)のガイドを追加する

## 背景

11/30までに動画50本(3日に1本)を公開する計画がIssue #168で確定した。台本テンプレ(#166)とAI音声の速度・尺(#165)は決定済みだが、アプリ開発から動画公開・サイト更新までの工程全体をつなぐ手順が文書化されておらず、毎サイクル「次に何をするか」を思い出すコストと抜け漏れの温床になっていた。

## 決定したこと

- `docs/guides/video-production-sop.md`を追加する。
- SOPは3日サイクル(D1 アプリ開発4h / D2 台本1.5h+AI音声0.5h+録画 / D3 編集〜公開)の工程と時間上限だけを持つ。
- 決定事項の中身はIssue #165 / #166 / #168への参照に留め、複製しない。
- 公開準備・release停止・同時公開は`docs/guides/app-development-cycle.md`を正とし、SOPは要点の再掲と参照のみ。
- 先行開発したアプリはPRを作らずbranchで待機させ、`dev`へ入れるのはそのアプリ自身のサイクルのD1で行う。
- 時間上限を超えそうなときは品質ではなく仕様を削る、を工程の原則として明記する。
- 人間にしかできない作業(OG画像、About/Guideの本人文章、題材決め)は週次バッチとしてサイクルから分離する。
- `AGENTS.md`のドキュメント索引へ1行追加する。

## 理由

50本ペースの成立条件は「毎サイクルの判断を減らすこと」であり、工程表と時間上限を1枚に固定することが最も効く。一方で台本テンプレや速度などの決定はIssue側で今後も更新されうるため、ガイドへ複製すると二重管理になる。SOPには「順番と上限」だけを置き、「内容」はIssueと既存ガイドへ委ねる構成にした。

先行開発の待機ルールは、`dev`へ未公開アプリが複数重なると`app-development-cycle.md`のrelease停止ルールと衝突するため、SOP側で衝突しない置き場所(branch待機)を先に決めた。

## 検討した代替案

### app-development-cycle.mdへ動画工程を追記する

既存ガイドはアプリ側の公開フローとして完結しており、動画制作の時間上限や週次バッチは性質が違う。追記すると1つのガイドが育ちすぎるため、別ガイドにして索引で分けた。

### Issue #168のコメントだけで運用する

計画と足切りはIssueが正だが、毎サイクル参照する工程表をIssueコメントに置くと、リポジトリ内の他ガイドから参照できず、docsの索引にも載らない。手順はdocsへ、計画と実績はIssueへ、と役割を分けた。

### 各工程の詳細手順(編集ソフトの操作など)まで書く

編集テンプレやサムネテンプレはまだ作成中で、ツールの操作は変わりやすい。SOPは工程の骨格に留め、詳細は安定してから必要なら追記する。

## トレードオフ

- 時間上限(開発4h、編集5h→3.5h)は現時点の実測と目標であり、数本回すと実態とずれる可能性がある。SOP冒頭で見直し条件を明記して吸収する。
- 決定事項をIssue参照にしたため、SOP単体では完結せずIssueを開く手間が残る。二重管理の回避を優先した。
- 週次バッチの分離は、本人作業が滞ると公開直前で詰まるリスクがある。週次面談(#168)で在庫を確認する運用でカバーする。

## テスト・検証内容

- `npm run format:check`
- `npm run lint`
- docsのみの変更のため、アプリコード・テストへの影響なし。

## 今後の見直し条件

- 3日サイクルを数本回して、工程や時間上限が実態と合わないと分かったとき。
- 編集の圧縮目標(7月末4h、8月末3.5h)を達成または断念したとき。
- Issue #168の週次面談で足切りラインや計画自体が変更されたとき。
- 編集テンプレ・サムネテンプレが確定し、詳細手順を残す価値が出たとき。
