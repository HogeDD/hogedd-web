# 作業中に見つけた課題を積極的にIssue化する

## 背景

作業中にIssue範囲外の改善、不整合、技術的負債を見つけても、会話で共有するだけでは次の作業から参照できなくなる。一方、見つけた案を無条件にIssue化すると重複や推測だけのIssueが増え、現在の作業範囲も曖昧になる。

## 決定したこと

- 範囲外の改善、不整合、技術的負債を見つけたら既存Issueを検索する。
- 重複がなく、再現根拠と完了条件を説明できる課題は、目的ごとに小さいIssueへ分ける。
- Issueには、やること、やらないこと、完了条件を記載する。
- 未確認の推測だけではIssueを作らない。
- 新しくIssue化した内容は、ユーザーの合意なしに現在のbranchへ混ぜない。
- 追加したIssue番号を作業報告またはdecision logへ残す。

## 理由

課題をGitHub上へ残すことで、後続作業が経緯と優先順位を確認できる。重複確認と根拠を条件にすることで、Issue数を増やすこと自体が目的になるのを防ぐ。現在のbranchへ実装を混ぜないルールを併記し、積極的なIssue追加と変更範囲の限定を両立させる。

## 検討した代替案

### 作業報告だけに残す

その場では共有できるが、別セッションや共同開発者から発見しにくいため採用しない。

### 見つけた案をすべてIssue化する

取りこぼしは減るが、重複や根拠のない案が増え、優先順位を判断しにくくなるため採用しない。

## トレードオフ

- Issue作成と重複確認の時間が増える。
- 課題を見つけても、再現根拠や完了条件が整理できない段階では相談または観察に留める必要がある。

## テスト・検証内容

- `AGENTS.md`の現在のIssue分割、スコープ限定、secret禁止と矛盾しないことを確認する。
- `npm run format:check`を実行する。

## 今後の見直し条件

- 重複Issueや実行不能なIssueが増えたとき。
- Issue以外のbacklog管理方法を導入したとき。
