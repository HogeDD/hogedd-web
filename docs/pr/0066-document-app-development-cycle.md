# アプリ開発サイクルを文書化する

## 背景

ホームとAppsページの基盤が整い、新しいアプリを継続的に追加する段階へ入った。一方、既存のガイドはIssue、branch、PRなど一般的な開発手順が中心で、アイデア相談、MVP、追加改善、YouTube動画、本番公開をどの単位で進めるかはまとまっていなかった。

## 決定したこと

- 企画から本番公開までの流れを`docs/guides/app-development-cycle.md`へまとめる。
- 最初のIssueでは、アプリが最低限動くMVPまでを扱う。
- UI、画像、操作上の改善は、MVPを実際に確認してから小さいIssueへ分ける。
- アプリ本体とYouTube動画は同じ本番公開で案内する。
- 未公開アプリが`dev`へ入ってから公開準備が完了するまで、`dev → main`のreleaseを止める。
- 公開準備Issueは`dev`へのmergeで閉じず、本番とYouTubeの公開確認後に閉じる。
- commit、PR、CI、merge、Issue closeの順序を明記する。
- 次のアプリで一度運用してから、ガイド改訂とSkill化を検討する。

## 理由

アプリごとに必要な技術やUIは異なるため、完成形の雛形を先に固定するより、MVPを作って実物から次のIssueを判断する方が手戻りを抑えられる。

また、アプリrouteとYouTube動画の公開時期がずれると、ホーム、Appsページ、動画の案内が食い違う。未公開期間のreleaseを止めることで、追加の公開制御を実装せずに同時公開を守る。

## 検討した代替案

### アプリ専用の統合branchで完成まで育てる

通常のreleaseを続けられるが、各Issueのbaseとmerge先が通常フローと異なり、branch管理が複雑になるため採用しない。

### 本番環境だけrouteを非表示にする

`dev`へ小さくmergeしながら通常releaseを続けられるが、環境変数や公開判定、404制御が必要になる。現時点ではアプリ追加頻度より仕組みの複雑さが大きいため採用しない。

### 最初からCodex SkillやCLI generatorを作る

作業を短縮できるが、まだ一度も新しいサイクルを通しておらず、変わりやすい判断まで自動化する可能性があるため採用しない。

## トレードオフ

- 未公開アプリが`dev`にある間は、関係のない変更も通常のreleaseを待つ。
- 緊急の本番修正が必要な場合は、影響を確認した別手順が必要になる。
- 初回は人がチェックリストを確認するため、自動化より手間がかかる。

## テスト・検証内容

- PrettierによるMarkdownのformat check。
- `AGENTS.md`とオンボーディングから新しいガイドへ到達できることを確認する。
- ガイド内の手順が現在のbranch、PR、deploy方針と矛盾しないことを確認する。

## 今後の見直し条件

- 次のアプリを企画から本番公開まで進めたとき。
- release停止が他の変更を長期間妨げたとき。
- アプリ追加を複数回繰り返し、自動化する作業と判断が安定したとき。
